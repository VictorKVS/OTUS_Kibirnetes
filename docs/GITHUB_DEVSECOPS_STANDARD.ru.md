# FATHER / OTUS — стандарт безопасной разработки в GitHub

## Последовательность
Задача (Issue) → отдельная краткоживущая ветка → код → локальные тесты → Pull Request → CI → ревью → слияние → тег релиза → манифест поставки → доказательства эксплуатации.

## Ветки и изменения
- `main` — стабильная ветка; защитить правилами GitHub.
- `feature/*`, `fix/*`, `docs/*`, `security/*` — изолированная работа.
- После включения защиты не отправлять изменения напрямую в `main`; запретить force-push и удаление `main`.
- Коммиты: `feat:`, `fix:`, `docs:`, `test:`, `security:`, `chore:`.
- При наличии второго независимого человека — хотя бы одно его утверждение PR. Самопроверка AI-агента не равна независимому ревью.
- Выпуск при зелёных проверках; исключения только адресные, с обоснованием, ответственным и сроком.

## Требования безопасности
- MFA/passkeys и минимально необходимые права участникам.
- `GITHUB_TOKEN` по умолчанию только чтение. Не передавать секреты недоверенному `pull_request_target`.
- Включить доступные Secret Scanning, Push Protection, Dependabot, CodeQL.
- Не коммитить `.env`, kubeconfig, ключи и конфиденциальные документы.
- Плановое развитие: Gitleaks, Semgrep, Trivy/Checkov, проверка Kubernetes YAML и SBOM.
- Сторонние GitHub Actions закреплять полным commit SHA после проверки источника. **Текущий стартовый workflow ещё использует major tags и не соответствует этому требованию.**
- Для облачных прав предпочитать OIDC/workload identity; избегать долгоживущих ключей.
- После настройки правил false positives небезопасные находки должны блокировать выпуск.
- Сохранять связи «угроза → контроль → тест → доказательство».

## Настройки владельца репозитория
1. GitHub Settings → Rules → Rulesets / Branches: обязательный PR, успешные проверки, запрет force-push/удаления, разрешение обсуждений, ограничение обхода.
2. Settings → Actions → General: минимальные права и разрешённые Actions.
3. Settings → Security / Advanced Security: включить доступные проверки и Dependabot; доступность зависит от репозитория/тарифа.
4. Включить двухфакторную аутентификацию для аккаунта.

## Ограничения текущей реализации
В начальном CI присутствуют Python unit-тесты, примитивная проверка шаблонов токенов и информационный аудит YAML (`continue-on-error`). **Это ещё не полноценный DevSecOps Gate**. Развёртывания Production и доступа к секретам этот CI не выполняет.
